## 1. 总体结论

工程纪律很强：进程所有权、资源账本、CSP 边界、WebSocket Upgrade 准入、官方审批接缝、失败路径测试都下了真功夫，几乎没有"伪造成功"的代码。**但这套纪律被执行得过了头，产品因此基本不可用。**

- 只有 Vue 3.4.27 + Vite 5.2.12 + plugin-vue 5.1.4 + macOS 这一个精确组合能跑。这个组合恰好是用户外部项目的版本。
- 默认约束 `mock-only` 会直接阻断 Vue 预览。
- 项目入口里只要有一个 `app.use(...)`，就必须手写 setup，而入口重放生成的草稿没有任何途径交到用户手上。
- 编译错误、运行时错误、被拦截请求的详情全部被脱敏成通用文案，Agent 无法据此修代码。
- 只要发生一次崩溃，账本残留就会永久锁死该工作区。
- Vue 2、Vue CLI、Element UI（用户明确的首要需求）一行未做；没有 Client UI；Linux/Windows 上任何路径都会直接抛错。

开发顺序偏离了 §16：大量投入在 Worker/SharedWorker/SW/JSONP/WS 等网络旁路的加固上，而"任意 Vue 项目能打开预览、看到错误"这条主路径没有打通。

**这份方案本身也有责任（Claude 起草）。**方案写了"只有通过验证的组合才声明支持""超出范围能力为 unknown，不默认放行""敏感值脱敏"，却没有区分"声明支持"和"允许运行"，也没说明脱敏的边界。开发方照字面执行，就得到了今天的结果。修正建议见 §6。

## 3. P0：阻断可用性或正确性

### P0-1 精确版本和平台门禁让 Vue 预览几乎无法使用

- **证据**：
  - `src/adapters/vue/vite/evidence.ts:4-13`：只有 `process.platform === 'darwin'` 且 vue/vite/plugin 的版本与测试版本字符串完全相等时，才把 scope 和 isolatedRender 设为 `supported`。
  - `src/adapters/vue/preflight.ts:30-35`：其余情况全部为 `unknown`。
  - `src/core/plan/planner.ts:104-106`：scope 不是 `supported` 就返回 `needs_configuration`。
  - Runner 侧还有两层硬编码：`src/adapters/vue/vite/runtime.ts:46`，以及 `worker.ts:76` 写死 `'5.2.12'`、`'3.4.27'`，`worker.ts:92` 写死 `'5.1.4'`。
- **影响**：Vue 3.4.28、Vite 5.4，或者任意 Linux 机器，都无法预览，而且没有任何配置能放行。同一套门禁被复制了 4 处。
- **建议（需 Aesc 决策）**：把"验证等级"和"允许执行"拆成两个概念。
  - 未验证的版本组合照常执行，在结果中带上 `unverified_toolchain` 诊断，能力保持 `unknown`。
  - Planner 只在 `unsupported` 或硬性 `requirements` 不满足时阻断。
  - 执行路径中删除所有版本字面量，版本范围只在 profile 或兼容矩阵中维护。

### P0-2 诊断被过度脱敏，Agent 无法据此修复代码

- **证据**：
  - `src/adapters/vue/vite/runtime.ts:106-107` 丢弃项目的全部 stdout/stderr；`worker.ts:114` 的 logger 遇到错误时只发送 `{type:'compile-error'}`，不带任何内容。
  - `runtime.ts:134` 和 `runtime.ts:147-148` 把编译错误、运行时错误、CSP 拦截都替换成固定英文句子。
  - `src/adapters/static/runtime.ts:73-76` 的 hint 写着 "Inspect the error in the local preview browser"，这对 Agent 毫无意义。
- **影响**：插件的核心价值是"Agent 改完代码后验证结果"。现在 Agent 只能知道"出错了"，不知道是哪个文件、哪一行、什么错误。
- **矛盾**：正在开发中的 `pageText`（`src/browser/bootstrap.js:92-109`，上限 2048 字）会把页面原文发给模型。脱敏策略自相矛盾：页面数据可以给模型，源码编译错误却不行。
- **建议**：统一制定一条脱敏规则，写进方案 §13。
  - **可以转发**：编译错误的 message、文件、行列和 code frame（截断）；运行时错误的 message 和前 N 帧堆栈（映射回源码）；被拦截请求的 origin + path（去掉 query）。
  - **必须去除**：env 值、nonce、URL 中的凭据和 query、Cookie、Authorization。
  - `pageText` 遵守同一规则。

### P0-3 崩溃后资源账本永久锁死工作区

- **证据**：
  - `src/shared/runner/ledger.ts:101-138`：`reconcile()` 只会报告，从不回收。临时目录仍在就算残留；进程存活就算残留；只要记录了 `pgid`，组长退出后也永远算残留。
  - `src/runner/process-tree.ts:110`：每个托管进程都记录了 `pgid`。
  - `src/host/runner-client.ts:178`：有残留就拒绝启动 Runner。
  - `src/runner/controller.ts:46-48`：有残留就拒绝 `start`。
  - 不存在任何回收工具或参数，文档也没写手工恢复方法。
- **影响**：Host 被强制结束一次，或 Runner 崩溃一次，这个工作区就再也无法预览，只能手动删除插件数据目录中的账本文件。方案 §9.2 写的是"提示或回收"，这里只实现了前半句。
- **建议**：
  - 插件临时根目录下自己登记的路径，直接删除。
  - PID + 启动时间一致的进程，按进程组终止。
  - 进程组残留：扫描进程表中 pgid 匹配的成员，逐个核对后终止；只有确实无法核对时才保留残留。
  - 给用户一个明确的恢复入口，例如 `page_preview_stop` 增加 `recover: true`，并输出将要回收的资源清单。

### P0-4 默认 `mock-only` 让 Vue 主路径默认失败

- **证据**：
  - `src/adapters/vue/preflight.ts:36`：Vue 所有网络通道都是 `none`。
  - `src/core/plan/planner.ts:117-126`：`mock-only` 要求浏览器的 4 个通道都是 mock 或 block。
  - `runtime.ts:45` 和 `worker.ts:71` 又各硬拒一次。
  - Planner 不允许请求方放宽已保存或默认的约束（`planner.ts:62`）。
- **影响**：项目必须在配置里显式写 `requirements: []` 或 `['isolated-target']`，Vue 预览才能打开；Agent 无法自行放宽。而 CSP、同源 Mock 中间件、WS 准入其实都已经实现，并有浏览器证据（`docs/vue-browser-network.md`）。
- **建议（需 Aesc 决策）**：二选一。
  - **A**：按已实现的机制如实声明浏览器通道（`browser-http` 为 mock/block，`browser-ws` 为 block，`service-worker` 为 block，来源 `response-layer`），`server-process` 只在使用 Node handler 时才要求。
  - **B**：isolated 路径的默认约束改为 `isolated-target`，`mock-only` 作为显式选项。
  - 推荐 A：它与方案 §4.2 的表格一致。

### P0-5 "适配任意 UI 组件库"的通用机制没有闭环

- **证据**：
  - `src/adapters/vue/preflight.ts:149-152`：没有 setup 时，只要入口中存在任何注册调用（实际项目几乎都有 `app.use(router/store/ElementPlus)`），就返回 `unsupported`："requires an explicit reviewed runtime.setup"。
  - `generateSetupDraft` 只在测试中被调用，没有任何工具或输出把草稿交给用户。
  - UI 库 profile 只用于在 `detect.ts:123-126` 打标签，没有参与任何决策或建议。
- **影响**：这是 Aesc 明确提出的需求（尽可能适配任意 UI 框架），实际交付结果是"所有项目都要手写 setup.js"。
- **建议**：
  - 遇到 `needs_configuration` 时，把草稿写入插件数据目录（或在用户同意后写入项目的 `preview/setup.draft.js`），并在结果中返回草稿路径、注册项分类和需要确认的业务模块。
  - 用户确认后进入现有的审批流程。
  - 第三方包的注册可以默认进入草稿；业务模块默认注释掉，并附上说明。

## 5. P2：过度设计与可维护性

1. **执行批准重复核验 5～6 次，带来的安全收益接近于零。** 核验点分布在 Planner（`planner.ts:127-130`）、审批后重开（`session-registry.ts:124-126`）、审批写入前（`execution-approval.ts:55-58`）、Runner start（`controller.ts:55-56`）、适配器执行前（`controller.ts:66`、`vite/runtime.ts:48-55`），以及 handler 导入前的专用 IPC 往返（`vite/runtime.ts:120-129`）。指纹只覆盖 command、env、setup 和 handlers，`vite.config`、业务源码和依赖都会照常执行，所以这套 TOCTOU 防线挡不住任何能改工作区文件的人。方案 §1.2 的前提本来就是"受信任工作区"。建议只保留"Planner 预检（用户体验）"和"Runner 执行前一次核验"两处，删除 handler 专用 IPC。
2. **三层进程、三套协议、两级账本。** 当前结构是 Host → Runner（每个工作区一个）→ Vite worker（每个预览一个），涉及 Runner IPC、worker 协议、handler 核验通道，账本也分 control 和 services 两级。首版限定一个工作区只有一个预览，Runner 与 worker 的隔离价值重叠。建议评估改为"Host 直接为每个预览托管一个执行进程"，可以去掉一层协议和一级账本。需要先做原型来比较，不要直接重写。
3. **Runner 控制器按适配器 ID 写死能力分支**（`controller.ts:60-62`：`adapter.id === 'vue-vite'`、`'static'`）。能力应该由适配器在契约中声明。
4. **代码可读性差。** `src/` 中有 455 行超过 160 字符，最长一行 1339 字符（`vue/preflight.ts:176`），还有多层嵌套三元表达式（例如 `vue/vite/runtime.ts:136`）。建议引入格式化工具（printWidth 120），并在 AGENTS.md 中写明。
5. **分层漂移。**
   - `src/core/config/*.ts`、`core/profile/detect.ts` 只是两行的兼容转发。项目尚未发布，不需要兼容层，应当删除。
   - `shared/` 里堆进了解析器、profile、账本、端口归属等领域逻辑，已经名不副实。
6. **文档变成了审计日志。**
   - 46 份文档中有 31 份记录 PID 或端口一类的一次性运行细节。
   - `docs/development-progress.md` 是无法阅读的长段落。
   - 部分文档已经过时，例如 `docs/configuration.md:5` 仍写着"ApprovalStore/用户批准交互尚未接通"。
   - 建议合并为：用户指南、配置参考、架构、兼容矩阵；运行证据移到 `docs/evidence/`，去掉 PID 和端口。
7. **一次性探针脚本长期留在仓库里。** `dev/` 和 `scripts/` 合计约 2.1k 行，大部分是 Phase 0 和单次验收用的 probe 或 verify 脚本。凡是已被测试覆盖的，删除；其余归档到 `tools/probes/` 并写明用途。
8. **调试信息只能靠 `lastError` 公共字段暴露。** 涉及 `session-registry.ts:82`、`controller.ts:26`、`session.ts:32`。失败时 Agent 拿不到原因，人也看不到，只有测试代码能读这个字段。建议在插件数据目录中写结构化的调试日志（经过脱敏），并在诊断中给出日志位置。
9. **Host 缓存只增不减。** `runner-client.ts:57-59` 的 `bindings`、`snapshots`、`diagnostics` 在停止后不会清理，而每次 `open` 都会生成新的 UUID。
10. **`pageText` 的性能问题。** 每次 DOM 变化（包括 class/style 属性变化）后，100ms 防抖读取一次 `innerText`，会强制重排。建议只在 `status` 请求时拉取一次，或者把频率限制到秒级。

## 6. UI/UX（面向 Agent、用户和审批）

- **工具输出**：
  - `renderResult` 仍然把整段 JSON 原样输出（`host/output.ts:37-40`，TODO 未处理）。capabilityGaps 中的长英文句子很占上下文。
  - 不带 `previewId` 调用 `status` 时，各预览的诊断被合并在一起，没有标注属于哪个预览（`session-registry.ts:175-176`）。
  - 建议改为三行摘要（状态、地址、是否最新）+ 能力缺口名称 + 带 previewId 的诊断。
- **等待窗口**：`open` 只等 2 秒（`session-registry.ts:46`）。Vite 冷启动通常更久，Agent 必然要轮询。建议默认等到目标就绪或 15 秒（可取消），或者提供 `waitMs` 参数。
- **hint 文案**：多处写着 "Inspect the local browser" 或 "configure and verify the state boundary"，这些是 Agent 无法执行的动作。每条 hint 都应该能直接转成下一次工具调用或配置改动。

- **接入成本**：当前接入一个 Element Plus 项目需要写 config、setup.js、`requirements`、`businessPaths`，还要经过一次审批，版本还必须精确匹配。目标应该是：零配置即可打开（使用入口草稿），只有需要场景数据时才写配置。
- **Client**：目前没有任何 UI，见 P1-10。
