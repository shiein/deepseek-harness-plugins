对应方案 §4.2、§6.2、§6.6、§7.3、§8、§11、§15.3。buildPlan 已实现统一策略/能力/批准读取规则；产品适配器的 probe/plan、应用识别与公共 open 尚待接入，因此本轮不是完整开页验收。

- 目标、配置和应用画像必须指向同一应用/规范根。默认保留配置 requirements，无配置约束时为 mock-only；单次请求不得放宽，重复约束也报错。不从工具参数生成用户批准。
- 明确请求策略优先，否则使用配置策略/适配器、显式 command/origin；未绑定的 auto 按 static→isolated→project→attach 选最小匹配路径。明确不能满足 scope/isolated-target 的 auto 候选先排除，同级多适配器要求配置；选定路径的预检失败后直接返回，不再尝试另一策略掩盖失败。
- 场景为显式请求→登记目标默认；未知场景失败，不选第一个。导航为明确 route 选择器→目标已有 route 上下文→场景 route；viewport 随本次请求传给适配器。模块 selector 和导航上下文分别保留，不把文件目标改写成路由目标。
- Adapter.plan 新增可选第四参数 AdapterPlanOptions（requirements/viewport/route）。Core 的适配器类型仅包含 probe/plan 等只读方法，没有 start。适配器必须返回与请求一致的项目/目标/选择器/scope/策略/场景/视口/导航/配置指纹，不能漏掉已配置断言或改变进程所有权。
- 必需 scope/独立渲染能力要有来源与覆盖说明，unknown/conditional 返回缺失条件，unsupported 明确失败。mock-only 核对 browser-http/ws/sse/service-worker，project 另核对代理和服务进程；没有完整 mock/block 控制、存在 observe/none 或只有 attach 观察能力时不能放行。
- command/env/setup/handler 指纹只读取并向只读 ApprovalStore.isApproved 查询，未批准返回 config_changed_needs_approval。没有调用 approve、执行命令、导入 setup/handler 或安装依赖。实际批准存储/用户确认入口与 Runner 执行前复核尚待实现。

PreviewPlan 新增可选 route（path/params/query），共享 IPC schema 同步接受。旧的无 route 计划仍有效，新字段需要两端同步构建；配置 JSON 不变。当前静态运行时不支持文件导航绑定，明确拒绝该请求；route 选择器附带不同导航上下文也拒绝，不忽略字段制造成功。
