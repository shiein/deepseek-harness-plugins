# 原生 DSH 的真实 HMR 验证

2026-10-31。结论：在自有受控响应层下，原生 DSH Browser 能执行 Vite 模块热更新，浏览器模块加载失败与服务端编译失败后均能修复恢复，交互计数不丢失。该证据属于构建器和载体探针，不代表 Vue 适配器或产品更新管线已经实现。

## 环境与执行边界

macOS `15.7.7` arm64；原生 DSH `0.2.1-rc.5`；Electron `44.7.0` / Chrome `152.0.7977.130`；独立 Node `24.13.1`；Vite `5.2.12`。Vite 来自用户机器现有的 `overview/web/node_modules/vite`，只读取其 manifest 和工具链包，不启动 overview 项目。

`tools/probes/phase0-hmr.mjs` 把 `tests/fixtures/vite-hmr` 复制到独立临时目录，使用最小环境启动。Vite 的 `configFile`、`envFile` 均为 false，cwd/root/cacheDir 都在临时样本内。没有读取 overview 的配置、`.env` 或业务源码，没有安装依赖、修改业务项目、调用模型或访问真实后端。

进程、端口和临时目录均登记到已有文件资源账本。最终使用官方 `middlewareMode`，由探针自己的 Node HTTP 服务承载 Vite 中间件和 HMR WebSocket，并统一处理停止。自有响应层注入 bootstrap 和 `connect-src 'self'`；未知业务请求返回 `404 unmatched_request`。没有用定时刷新、重启服务或模拟更新消息代替 HMR。

## 实际结果

| 阶段 | 页面与构建器证据 | 独立核对 |
| --- | --- | --- |
| 初始加载 | `revision-1`、`current`、bootstrap 先于业务模块 | bootstrap 在实际响应中早于 `/@vite/client` 与 `/main.js`；收到 document-loaded 和 revision-1 挂载报告 |
| 交互 | 点击后计数为 1 | 后续全过程保持 1 |
| 正常更新 | 临时 target.js 改为 revision-2，页面自动变为 current/revision-2 | 第二个目标挂载报告，document-loaded 仍只有一次 |
| 浏览器模块语法失败 | 裸 JS 的不完整赋值仍可被 Vite 返回为 HTTP 200，浏览器导入失败；页面显示 update_error 并保留 revision-2 | 不新增目标挂载，不能把 HTTP 200 或 HMR 连接当作更新成功 |
| 修复 | 改为 revision-3，页面自动恢复 current/revision-3 | 第三个目标挂载报告；无整页重载 |
| 编译失败 | 改为导出缺失模块；Vite import-analysis 报 `Failed to resolve import`，含文件和位置；页面保留 revision-3 并显示加载失败 | 未产生第四个成功挂载；服务进程仍存活 |
| 再修复 | 改为 revision-4，页面恢复 current/revision-4 | 第四个目标挂载报告，计数仍为 1 |

最终脚本实际输出：

```json
{"step":"verify","verifiedMounts":["revision-1","revision-2","revision-3","revision-4"],"documentLoads":1,"processUnchanged":true,"sourceChanged":false}
```

每步都核对 PID 与启动时间、账本登记的临时路径、目标挂载顺序及 CSP 违规数量；最终无 CSP 违规。UI 通过原生桌面无障碍树和截图检查，页面更新状态与交互计数另行观察。**报告中的 target-mounted 是样本自身信号，不是通用业务就绪判定。**

## 实测中修正和确认的机制

- Vite 5 客户端会从解析后的真实包路径 import `dist/client/env.mjs`。初版白名单拒绝它，导致文档已加载而目标未初始化。修订只允许这个具体文件，其他 `/@fs/` 路径继续拒绝；回归测试覆盖精确许可和未知路径拒绝。
- 模块更新回调可以得到 undefined，初版样本因此停在 updating。现改为明确的 update_error，并已实测该分支和后续恢复。
- 不能只监听 `vite:error` 来收集全部编译失败。部分错误经 HTTP 模块转换暴露，Browser 只得到加载失败，完整诊断在 Vite 服务端。因此产品适配器仍需把构建器诊断接入 Runner，不能从通用页面错误反推编译成功或失败详情。
- 本版本对部分不完整 JS 的错误定位还出现过 `offset is longer than source length`；没有修改或升级 Vite 来掩盖它。最终编译失败判定使用缺失模块的实际 import-analysis 错误，裸 JS 解析失败单独验证为模块加载失败。
- 初轮清理检查发现，非 middlewareMode 的 Vite 自带 SIGTERM 处理会在关闭服务后直接 process.exit，抢先中断探针的临时目录与账本清理。已改为 middlewareMode + 自有 HTTP 服务，并重跑全部原生 HMR 步骤。新增真实子进程回归验证 SIGTERM 后正常 exit 0、端口释放、临时目录删除、账本为空；未用强制清空记录来冒充进程退出。

## 复现

1. 准备 Node 24 和明确的已安装 Vite 5.2.12 包目录。运行 `node tools/probes/phase0-hmr.mjs <Vite包绝对目录> <输出绝对目录>`；实际检查使用仅包含 PATH/TMPDIR 的环境。脚本拒绝其他 Vite 版本，不自动安装。
2. 在原生 DSH 创建本轮 Browser tab，打开脚本输出的 loopback origin。确认 revision-1 和 bootstrap 顺序，点击计数按钮一次。
3. 依次运行 `node tools/probes/phase0-hmr-step.mjs <输出绝对目录> <步骤>`。步骤顺序为 `update`、`module-error`、`recover-module`、`compile-error`、`recover-compile`、`verify`。每一步后观察 Browser，再执行下一步；不能连发写入跳过错误画面。
4. 观察顺序为 revision-2 → update_error/旧画面 → revision-3 → 编译日志和加载失败/旧画面 → revision-4。期间不点击整页刷新，不重启服务；计数始终为 1。
5. 关闭本轮 tab，核对保存的进程身份后给探针发送 SIGTERM。探针关闭 Vite、删除临时副本并释放资源账本，脱敏证据保留在输出目录。
6. 单独运行 `node tools/probes/verify-phase0-hmr-cleanup.mjs <Vite包绝对目录> <独立输出绝对目录>`，可自动复现真实 Vite 子进程的 SIGTERM 清理回归，无需操作 DSH。

本次最终证据位于忽略目录 `output/phase0/hmr-managed`，自动清理回归位于 `output/phase0/hmr-cleanup`；初轮观察位于 `hmr` 与 `hmr-final`，其中旧模式残留由启动者确认原 PID/端口消失后，按账本的精确临时路径补清理，记录标注 externalCleanup。原始 fixture 保持 revision-1。最终模式 SIGTERM 已自动完成清理，且四个测试账本均为空；用户 DSH 与原有输入保持原样。

验证：`npm run typecheck`、`npm run build`、新增脚本/浏览器 ESM 语法检查通过；`npm test` 为 tests 32、pass 32、fail 0、skipped 0。真实 SIGTERM 回归实际输出为 `Real Vite SIGTERM: exit 0; temporary root removed; resource ledger empty; port released`。仅此版本、原生载体与原生 ESM 组合有证据；web iframe HMR、Vue SFC、CSS HMR、其他构建器、跨工作区存储和完整 Runner 更新诊断仍未据此验收。
